## 两项代码层面的发现

### 1. 粤语检查存在可复现漏检

当前 [import_pair_v2.py](D:/dev/projects/fourlang_translation/scripts/supplemental/import_pair_v2.py:40) 的粤语模式不包含“而家”。对包内实际例句运行现有检查得到：

```json
{
  "cantonese_regex_matches": false,
  "import_gate_rejection": null,
  "audit_hints": []
}
```

这说明当前导入规则和基于字符比例的审查提示均不能发现该例。不能把“存在汉字”“繁体已转简体”当作“符合普通话”。本地复现与样本现象一致，但没有据此证明服务器历史版本的完整流转路径。

修复建议：共享普通话语体检查、覆盖确定的粤语短语、加入正反例回归测试。此类规则只能补明显漏检，不能完成语义质量验收。不可简单全局替换粤语词后把样本当作已校对译文。

### 2. UNKNOWN 可能是旧导出步骤丢失审核元数据

当前 [data_flow.py](D:/dev/projects/fourlang_translation/scripts/pipeline_v2/data_flow.py:714) 的旧 KD 流程先筛选解析成功、PASS、HIGH/MEDIUM，再导出训练行；但其输出未保存 judge_label 和 teacher_id（约 767–779 行）。

因此，“UNKNOWN”不能直接等同于“未审核”或“不合格”。需要回查对应原始审核产物，按方向和精确文本关联；不能仅凭旧代码推断所有 UNKNOWN 都应该改成 PASS。无法唯一关联的条目应保留不确定状态。

同一流程把原始训练行标记为 human_replay，这个字段本身并不证明人工逐句审定。
